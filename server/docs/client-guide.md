## 1. 接入前准备

### 1.1 获取必要信息

| 信息 | 来源 | 示例 |
|---|---|---|
| 服务端地址 | 运维提供 | `ws://linksee.example.com:8000` |
| 共享密钥 | 运维下发 | `a3f8b2c1...` |
| 设备 ID | 固件生成 | `glass-001` |

### 1.2 设备 ID 规范

- 每台设备持有唯一 ID，建议格式：`{型号}-{序列号}`，如 `glass-A01-0001`
- 设备 ID 在固件首次启动时生成并持久化，之后不变
- 不要用 MAC 地址——某些平台不允许读取，且设备更换网卡后会变

### 1.3 密钥安全

- **不要硬编码到固件镜像源码中。** 应存储在安全区域（如 TEE/secure element），或通过出厂配置注入。
- 密钥轮换时固件应能从服务端获取新密钥（通过 OTA 或单独的配置接口）。
- 首期至少做到：密钥不跟着固件二进制一起分发到公开渠道。

## 2. 鉴权

### 2.1 算法

```
token = HMAC-SHA256(secret, device_id).hexdigest().lower()
```

即：用共享密钥对设备 ID 做 HMAC-SHA256，取**小写十六进制**字符串。

### 2.2 实现参考

**Python**:
```python
import hashlib, hmac
token = hmac.new(secret.encode(), device_id.encode(), hashlib.sha256).hexdigest()
```

**C (mbedtls)**:
```c
#include <mbedtls/md.h>

int compute_token(const uint8_t *secret, size_t secret_len,
                  const char *device_id,
                  char token_out[65]) {
    uint8_t hash[32];
    mbedtls_md_hmac(
        mbedtls_md_info_from_type(MBEDTLS_MD_SHA256),
        secret, secret_len,
        (const uint8_t *)device_id, strlen(device_id),
        hash
    );
    for (int i = 0; i < 32; i++)
        sprintf(token_out + i * 2, "%02x", hash[i]);
    token_out[64] = '\0';
    return 0;
}
```

**JavaScript (测试用)**:
```javascript
// 浏览器/Node.js 均可用 Web Crypto API
async function token(deviceId, secret) {
  const enc = new TextEncoder();
  const key = await crypto.subtle.importKey(
    "raw", enc.encode(secret), { name: "HMAC", hash: "SHA-256" }, false, ["sign"]
  );
  const sig = await crypto.subtle.sign("HMAC", key, enc.encode(deviceId));
  return Array.from(new Uint8Array(sig)).map(b => b.toString(16).padStart(2, '0')).join('');
}
```

### 2.3 传递方式

WebSocket 放查询参数、HTTP 放请求头，详见 [`api.md` §2](api.md#2-鉴权)。

### 2.4 Token 特点

- **不需要请求服务端获取**——客户端自己算，零网络开销
- **不包含时间戳**——不会过期，计算一次可以复用
- **不跨设备**——device_id 不同则 token 不同，A 设备的 token 在 B 设备上无效
- 建议启动时计算一次并缓存，不要每帧都重新算

## 3. 建立连接

### 3.1 选择通道

| 场景 | 使用 |
|---|---|
| 正常使用 | **WebSocket**（主通道） |
| WebSocket 不可用时 | HTTP POST（备用通道） |

WebSocket 是推荐通道，因为：
- 长连接，推帧不需要重复 TCP 握手
- 支持服务端主动推送（阅读模式分片连续下发）
- 有心跳保活

### 3.2 WebSocket 连接

```
ws://<host>/ws/glass/{device_id}?token=<token>
```

**连接流程**：

```
1. 计算 token
2. 发起 WebSocket 连接
3. 服务端返回 101 Switching Protocols → 连接成功
   服务端 close code 4401 → 鉴权失败（检查 secret 和 token 计算）
4. 开始推帧
```

**重连策略**：

```
断连 → 等待 3 秒 → 重新连接
            ↓ 失败
       等待 6 秒 → 重新连接
            ↓ 失败
       等待 12 秒 → ...（指数退避，上限 60 秒）
```

> 重连后视为新会话，服务端会重置该设备的帧比较基准。上一次的上下文不会残留。

### 3.3 HTTP 备用

```
POST http://<host>/v1/frame
Content-Type: application/json
X-Device-Token: <token>

{
  "device_id": "glass-001",
  "seq": 12,
  "trigger": "auto",
  "image": "<base64>"
}
```

- 无连接状态，每次请求独立
- 阅读模式的分片通过 `segments` 数组一次返回（不能逐条推送）
- 没有背压语义——调用方同步等待

## 4. 推帧

### 4.1 三种模式

| trigger | 含义 | 典型场景 |
|---|---|---|
| `auto` | 自动推帧 | 正常行走，摄像头持续采集 |
| `manual` | 用户主动按键 | 用户按了"这是什么"按钮 |
| `read` | 阅读模式 | 用户对着菜单/说明书按"读这个" |

### 4.2 自动推帧（最常用）

```
┌──────────────────────────────────────────────────┐
│ 摄像头采集帧                                      │
│   ↓                                               │
│ 缩放到长边 ≤ 1024px、JPEG q ≈ 75（见 §8）         │
│   ↓                                               │
│ base64 编码（不带 data: 前缀）                     │
│   ↓                                               │
│ 发送 JSON: {"type":"frame","seq":N,"trigger":"auto","image":"..."}  │
│   ↓                                               │
│ 等待响应，按 §5 处理                                │
│   ↓                                               │
│ 1-2 帧/秒循环                                     │
└──────────────────────────────────────────────────┘
```

**帧率**：1-2 帧/秒即可。服务端限流 1 次/秒，推更快只会被丢弃。

**seq 管理**：每发送一帧 seq 递增（建议用 uint32 回绕）。seq 用于对齐请求和响应，不要依赖「发 N 帧收 N 条响应」这个假设（见 §4.5）。

### 4.3 用户手动触发

```json
{"type":"frame","seq":42,"trigger":"manual","image":"<base64>"}
```

与 auto 的区别：
- **跳过去重**：用户按两次按钮拍同一场景，两次都要给出结果
- **跳过场景门控**：不计入 3 秒间隔
- **仍受限流**：1 次/秒，连按不会得到更多结果

### 4.4 阅读模式

见 [§7](#7-阅读模式)，流程较特殊。

### 4.5 理解背压

**服务端只保留最新 1 帧。** 如果上一帧还在处理，新帧会直接替换旧帧，旧帧被静默丢弃。

```
客户端推帧:  seq=1 → seq=2 → seq=3 → seq=4
             ↓
服务端处理:  [处理 seq=1, 耗时 1.5s]
             中途 seq=2 覆盖 seq=1
             中途 seq=3 覆盖 seq=2
             中途 seq=4 覆盖 seq=3
             ↓
客户端收到:  seq=4 的响应（只有一条）
             seq=1,2,3 被静默丢弃
```

**正确做法**：
- 用 `seq` 对齐响应，不要数收到的条数
- 推帧频率不要超过 2 帧/秒（服务端处理能力固定，推更多只会增加丢弃率）
- 被丢弃的帧不影响后续帧的处理

## 5. 处理响应

### 5.1 响应结构

```json
{
  "type": "<消息类型>",
  "content": "<文案内容>",
  "seq": 12,
  "latency_ms": 1340,
  "index": 1,
  "total": 1,
  "end": true
}
```

完整字段定义见 [`api.md` §3.4](api.md#34-下行结果消息)。

### 5.2 消息类型处理

> 完整定义见 [`api.md` §6](api.md#6-消息类型速查)。

| type | 固件动作 |
|---|---|
| `alert` | **震动 + 语音播报 + 屏幕显示** content |
| `voice` | **语音播报 + 屏幕显示** content |
| `text` | **屏幕显示** content（不震动不播报） |
| `noop` | **不做任何事，保持当前显示不变** ⚠️ |
| `read` | **入队顺序播报**（见 §7），按 index/total/end 控制进度 |
| `error` | 屏幕显示 content，**连接不断** |

### 5.3 ⚠️ `noop` 是最容易被做错的一条

服务端判定本帧和上一帧是同场景，跳过处理。

**错误做法**：清空屏幕 → 用户看到画面不停闪烁
**正确做法**：**屏幕保持上一结果不变，不震动、不播报、不改变 UI 状态**

### 5.4 用 seq 对齐响应

```
发送:  seq=100, trigger=auto
收到:  seq=100, type=alert, content="红灯，请等待"  ✓ 对齐

发送:  seq=101, trigger=auto
（被闸门驳回，seq=101 的帧被丢弃）

发送:  seq=102, trigger=auto
收到:  seq=102, type=text, content="前方便利店"      ✓ 对齐
```

> 收到 seq=102 的响应时，跳过了 seq=101——这是正常的，不要报错。

## 6. 心跳保活

### 6.1 发送心跳

```json
{"type": "ping"}
```

服务端回复：
```json
{"type": "pong"}
```

### 6.2 心跳周期

- **建议间隔**：10-15 秒
- **超时判定**：连续 30 秒未收到 pong → 断开重连
- 心跳也同时刷新了服务端的在线状态（TTL 30 秒）

### 6.3 实现建议

```
每秒 tick:
  if 距离上次 ping > 15 秒:
    发送 ping
  if 距离上次 pong > 30 秒:
    断开 + 重连
```

## 7. 阅读模式

用户主动对着菜单、说明书、告示牌触发，服务端把画面文字逐字读出。

### 7.1 发起

```json
{"type":"frame","seq":7,"trigger":"read","image":"<base64>"}
```

### 7.2 响应：连续 N 条分片

```json
// 第 1 片 — 还没结束
{"type":"read","content":"川菜馆菜单，凉菜类：","seq":7,"index":1,"total":8,"end":false}

// 中间片都有 end:false
{"type":"read","content":"口水鸡 38 元，夫妻肺片 42 元","seq":7,"index":2,"total":8,"end":false}
...

// 最后一片
{"type":"read","content":"完","seq":7,"index":8,"total":8,"end":true}
```

### 7.3 固件处理流程

```
收到 end=false → 入本地播放队列，继续等
收到 end=true  → 入队列，标记本次阅读结束
               ↓
         按 index 顺序播放（服务端保证按序下发）
         可以显示 "3/8" 这类进度
```

### 7.4 中途中断

```
用户转头 / 按键 / 手势中断
        ↓
固件清空本地播放队列
        ↓
不要给服务端发任何东西
```

> 服务端不维护播报进度——这是它能保持无状态、任意 worker 处理任意设备的前提。

### 7.5 特殊情况

| 情况 | 收到的响应 | 处理 |
|---|---|---|
| 画面无文字 | `{"type":"text","content":"未发现文字","end":true}` | 显示文本即可，**不是** read 类型 |
| 连按太快超限 | `{"type":"text","content":"阅读太频繁，请稍后再试"}` | 显示提示，**不是** noop |
| 画面里只有一句话 | 可能只有 1 片 `{"end":true}` | 正常播报 |

## 8. 图像规范

> 完整要求见 [`api.md` §9](api.md#9-图像预处理约定)。

### 8.1 核心要求

| 参数 | 要求 |
|---|---|
| 分辨率 | **长边 ≤ 1024px** |
| 格式 | **JPEG** |
| 质量 | **q ≈ 75** |
| 编码 | base64，**不带 `data:` 前缀** |
| 上限 | base64 后 ≤ 6MB |

### 8.2 固件做 vs 服务端补做

```
最佳实践：固件采集后立刻缩放编码，再送给服务端
          ↓ 好处：减少网络传输量 + 省掉服务端解码重编码
```

如果固件做不到（如算力不足），服务端会补做缩放，但代价是：
- 固件上传了更大的图（浪费带宽）
- 服务端多一次解码+编码（20-40ms）

### 8.3 软性上限

- JPEG base64 后 ≤ **6MB**（约 4.5MB 原图）
- 超出返回 HTTP 422

## 9. 异常处理

### 9.1 协议错误

```json
{"type":"error","content":"bad_frame: base64 解码失败: ...","seq":0}
```

收到 error 后：
- **连接不会断开**
- 可以继续发送后续帧
- 不要因为一条 error 就触发重连

### 9.2 连接断开

```
断开场景          处理
──────────────────────────────
服务端主动断开      按重连策略重试
网络中断            按重连策略重试
心跳超时（30s）     主动断开 + 重连
收到 close 4401     鉴权失败，检查 secret
```

### 9.3 服务端故障

| 表现 | 客户端行为 |
|---|---|
| 连接不上 | 重连退避，不阻塞 UI |
| 连接成功但无响应 | 心跳超时 → 重连 |
| 连续出现 error | 继续推帧，不重连 |
| 收到"识别失败"兜底文案 | 显示给用户，继续推下一帧 |

### 9.4 常见错误速查

> 完整错误码参考 [`api.md` §8](api.md#8-错误码参考)。

| 表现 | 原因 | 解决 |
|---|---|---|
| close 4401 | token 错误 | 检查 shared_secret |
| HTTP 401 | 请求头缺失或错误 | 检查 X-Device-Token |
| HTTP 422 | image 为空或超长 | 检查 image 字段 |
| 收到 `error` 消息 | base64 解码/协议错误 | 连接不断，继续推帧 |
| 连续收到 `noop` | 场景没变化，正常 | 不要清屏 |

## 10. 接入自检清单

在联调之前，先逐项验证：

### 基础连接

- [ ] 正确 token 能连上 WebSocket
- [ ] 错误 token 收到 close 4401
- [ ] 断连后 3 秒内能重连

### 心跳

- [ ] 发 ping 收到 pong
- [ ] 30 秒没收到 pong 触发重连

### 正常帧

- [ ] `trigger=auto` 推帧能收到响应
- [ ] `alert` → 震动 + 语音 + 显示
- [ ] `voice` → 语音 + 显示
- [ ] `text` → 仅显示
- [ ] **`noop` → 不清屏，保持上一个结果** ⭐
- [ ] `error` → 显示错误提示，连接不断

### 手动触发

- [ ] `trigger=manual` 推帧能收到响应
- [ ] 同一张图连续两次 manual 都得到结果（不去重）

### 阅读模式

- [ ] `trigger=read` → 收到连续 N 条分片
- [ ] `end=false` 时继续等待，`end=true` 时结束
- [ ] 分片按 index 顺序播放，不乱序
- [ ] 所有分片的 `seq` 相同（不是 N 个不同的帧）
- [ ] 播放到一半转头 → 清空本地队列，不给服务端发东西
- [ ] 无文字画面收到「未发现文字」
- [ ] 连按超限收到「阅读太频繁」

### 图像

- [ ] 上传的图长边 ≤ 1024px
- [ ] JPEG 质量 q ≈ 75
- [ ] 不带 `data:` 前缀

### 鲁棒性

- [ ] 快速连推 10 帧不卡死、不因收不全响应而崩溃
- [ ] 收到 error 后可以继续推帧
- [ ] 中文文案显示不截断、不乱码
- [ ] `seq` 回显对齐正确
