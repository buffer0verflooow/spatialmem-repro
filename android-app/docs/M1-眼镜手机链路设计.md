## 1. M1 要交付什么

PRD M1 的退出条件是四条：30 分钟连续运行不崩、重连 ≤5s、端到端 p95 ≤700ms、**下游算法零改动**。

拆成六块：

| # | 内容 | 状态 |
|---|---|---|
| 1 | 线格式与包复用 | ✅ 已实现 + 单测 |
| 2 | 跨设备时钟对齐 | ✅ 已实现 + 单测 |
| 3 | 过期帧丢弃、丢包统计 | ✅ 已实现 + 单测 |
| 4 | 连接状态机与重连 | ✅ 已实现 + 单测 |
| 5 | 眼镜端 App（采集/编码/发送/播报/触控） | ⛔ 待 M0 |
| 6 | 手机端接收（解码 → `VideoSource`） | ⛔ 待 M0 |

**为什么 1–4 可以先做**：它们不依赖任何设备参数。分辨率、帧率、编码器、TTS 可用性这些
M0 才能确定的东西，在设计上被推到了**运行时握手协商**（见第 4 节），
所以 M0 的结论只改变协商的默认值，不改变代码结构。

## 3. 传输选型

### 3.1 为什么是 TCP，不是 WebRTC

| 方案 | 取舍 |
|---|---|
| **TCP（选定）** | 局域网点对点、两端都由我们控制，不需要 NAT 穿透、ICE、DTLS 协商。控制消息天然可靠有序 |
| WebRTC | 为一条局域网点对点链路引入一整套依赖；且它的拥塞控制会**替我们决定丢哪帧**，而我们要按「帧年龄」自己决定（F6-8） |
| UDP 自研 | 控制通道要自己做可靠传输，等于重造一部分 TCP |

### 3.2 单连接 + 通道复用，而不是多连接

多连接会带来「控制通道活着但媒体通道死了」这类半死状态，判活逻辑显著复杂化。

代价是**队头阻塞**：一个大视频包会占住 socket 写缓冲，控制包排在后面会被压住。
量化一下最坏情况：

```
640×360@15FPS，1.5Mbps 平均 → 平均帧约 12.5KB
关键帧约 50KB
Wi-Fi Direct 有效带宽保守取 10Mbps
→ 50KB / 10Mbps ≈ 40ms
```

40ms 在 700ms 端到端预算内可接受。缓解手段是**控制类通道在发送队列里插队**
（`LinkChannel.isHighPriority`），这样阻塞只剩「当前正在写的那一个包」，
而不是「队列里所有积压的视频包」。

> 若 M0 实测 Wi-Fi Direct 有效带宽显著低于 10Mbps，这个 40ms 会等比放大，
> 届时需要把关键帧切片发送。切片点已经预留：`LinkFlags` 有空余位。

### 3.3 线格式

头部固定 20 字节，大端：

```
偏移  长度  字段
0     2    magic 'B''A'
2     1    version
3     1    channel
4     1    flags
5     3    payload 长度
8     4    sequence（每通道独立，uint32，允许回绕）
12    8    发送方单调时钟纳秒
20    …    payload
```

三个设计点：

1. **时间戳一律是发送方自己的单调时钟**，线格式不做任何跨设备换算。
   换算是接收侧的事，这样线格式不依赖于对齐是否已收敛。
2. **长度有硬上限**（默认 2 MiB）。一个损坏或恶意的长度字段不得导致巨额分配——
   这是竞品分析 R0-1 里「包长有上限」那条要求的落点，有单测覆盖。
3. **流错位不尝试重同步**，直接抛异常让调用方断开重连。在字节流里重新找 magic
   很可能找到「看起来合法但实际是负载中段」的伪包头，那比断开危险。

通道：

| 通道 | 码 | 方向 | 内容 |
|---|---|---|---|
| VIDEO | 0x01 | 上行 | H.264 访问单元，一包一帧 |
| AUDIO | 0x02 | 上行 | PCM16 或 Opus（握手协商） |
| IMU | 0x03 | 上行 | IMU 采样批 |
| POSE | 0x04 | 上行 | 姿态采样批 |
| INPUT | 0x05 | 上行 | 镜腿触控、佩戴状态 |
| CONTROL | 0x10 | 双向 | 握手、心跳、时钟对齐 |
| SPEAK | 0x11 | **下行** | 播报文本或 promptId |
| SPEAK_STATUS | 0x12 | 上行 | 播报生命周期回执 |

## 4. 能力协商 —— M1 不必等 M0 的关键

眼镜端 HELLO 声明**实测能力**，手机端 HELLO_ACK 下发会话配置：

```kotlin
GlassCapabilities(
    videoModes = [...],          // 相机实际能交付的组合（M0 Q2）
    hasHardwareAvcEncoder,       // M0 Q9
    hasLocalChineseTts,          // M0 Q5 -> 决定 SpeakPath
    hasRotationVector, hasSixDof,// M0 Q3
    hasTempleTouch,              // M0 Q4
    hasWearDetection             // M0 Q6
)
        ↓
SessionConfig(videoWidth, videoHeight, videoFps, videoBitrateBps,
              enabledChannels, speakPath, heartbeatIntervalMs, clockSyncIntervalMs)
```

于是 M0 的每个答案都变成运行时配置，而不是编译期常量。**M0 若发现某项不可用，
改的是协商默认值和降级分支，不是代码结构。**

`SpeakPath` 三档直接对应 PRD 决策 D2 及其兜底：

| 档 | 条件 | 说明 |
|---|---|---|
| `GLASSES_LOCAL_TTS` | M0 Q5 判定中文 TTS 可用 | D2 首选 |
| `GLASSES_PRESET_AUDIO` | 中文 TTS 不可用，或高风险提示要省掉合成耗时 | 手机下发 promptId |
| `PHONE_TTS_BLUETOOTH` | 前两者都不行 | 要接受 Wi-Fi/BT 2.4GHz 共存的延迟抖动 |

## 5. 跨设备时钟对齐（本轮最要紧的一块）

### 5.1 为什么非做不可

`VideoFrame.captureTimestampNs` 会一路流到 `GuidanceCommand.captureTimestampNs`，
再由 `GuidanceEvent.captureToEventLatencyMs` 算端到端延迟。

两台设备的 `elapsedRealtimeNanos()**各自从自己开机起算**，偏移是任意的。
不做换算，这个「延迟」不是「慢了多少毫秒」，而是**两台设备开机时间差**——
可能是负的一小时。同时 `TemporalDistanceEstimator` 的速率计算和 `RiskEngine`
的冷却窗口也会一起错。

有一条单测专门锁住这个失效模式：
`withoutConversionTheLatencyWouldBeTheClockOffsetNotTheRealDelay`。

### 5.2 算法

NTP 四时间戳往返，走 CONTROL 通道：

```
手机 ──PING──▶ 眼镜
 t1=localSend      t2=remoteRecv
 t4=localRecv ◀──PONG── t3=remoteSend

offset(眼镜−手机) = ((t2−t1) + (t3−t4)) / 2
rtt               = (t4−t1) − (t3−t2)
手机时钟域 = 眼镜时间戳 − offset
```

**选样：取 rtt 最小的样本。** 理由是误差上界正好是 rtt/2：

> 设去程单向延迟 d1、回程 d2，则 d1+d2 = rtt。测得偏移与真实偏移之差等于
> (d1−d2)/2，其绝对值在 d1 或 d2 取到 0 时最大，即 rtt/2。

这是**不依赖任何分布假设的确定性上界**，所以可以直接拿来支撑验收结论。
这比「多样本取平均」更适合安全相关判断——平均值的误差需要分布假设，上界不需要。

### 5.3 收敛门槛正好对应 F6-9

PRD F6-9 要求跨源时间戳误差 ≤ 50ms。由 `uncertainty = rtt/2` 得：**要求最优样本 rtt ≤ 100ms**。
默认 `maxUncertaintyNs = 50ms`，且要求至少 3 条样本。

**未收敛时不允许换算**：`toReceiverNs()` 返回 null。诊断用的
`toReceiverNsUnchecked()` 单独提供，且注释明确写了安全路径不得使用。

### 5.4 抗漂移

晶振漂移约 20 ppm ≈ 72ms/小时，会吃掉整个 50ms 预算。两个对策：

1. **样本窗口按时间淘汰**（默认 120s），不只按条数。否则一条很早的低 rtt 样本会永久压住估计值；
2. **周期性再同步**（默认 30s）。

有单测用实测漂移反推同步周期够不够：20 ppm 下 30 秒周期末的额外误差约 0.6ms（远小于预算），
而一小时不同步会到 72ms（超预算）。**这条测试固定了推算方式**，真机拿到实测漂移后
可直接算出该用多长周期。

### 5.5 重连必须清空

任一端睡眠或重启都会让偏移跳变，旧样本会变成「自信但错误」的信息。
`LinkAction.StartClockSync` 隐含 reset 语义，状态机在每次握手完成后都发这个动作
（不只首次），有单测覆盖。

## 6. 过期帧丢弃与统计

### 6.1 StaleFrameGate（F6-8）

用旧画面播报比不播报更危险：用户已经走过去了，系统还在说「前方有椅子」。
超过 400ms 的帧在进入风险判断前丢弃。

**对齐未收敛时仍要能工作**：退而用包到达时间算年龄。这个值系统性地**低估**真实年龄
（少算了采集到到达的传输耗时），所以是下界，结果标记为 `ARRIVAL_LOWER_BOUND`。

- 下界超阈值 → 一定该丢；
- 下界没超 → 不能断言不该丢，由上层决定是否更保守。

另外，对齐误差或时钟跳变可能让时间戳**超前于**当前时刻，产生负年龄。
这必须夹到 0，而不能当成「非常新」——有单测覆盖。

`acceptedWithoutSyncCount` 这个计数器应随对齐收敛而停止增长；持续增长
就是 F5-5 watchdog 该报警的信号。

### 6.2 SequenceTracker

丢包/乱序/重复统计，供会话总结与 F6 验收（丢帧率 ≤ 5%）。三个易错点都有单测：

1. **uint32 回绕**：0xFFFFFFFF → 0 是正常前进，不是丢了 40 亿个包；
2. **迟到包抵消**：先前记的丢失要减回来，否则丢包率被系统性高估；
3. **对端重启**：序号从头开始，要重建基线而不是记一大笔丢包。

## 7. 连接状态机与重连

```text
IDLE ──Start──▶ CONNECTING ──Connected──▶ HANDSHAKING
                                              │HandshakeCompleted
                                              ▼
                            STREAMING ◀──ClockConverged── SYNCING
                                │
                    掉线/心跳超时│
                                ▼
                          RECONNECTING ──退避后重连──▶ HANDSHAKING
```

**时钟未收敛不进 STREAMING** —— 否则会用未对齐的时间戳做安全判断。

### 7.1 退避表与 5 秒目标

默认 `[250, 500, 1000, 2000]` 之后恒为 2000ms。失败发生在 t=0 时，
重试点为 **0.25 / 0.75 / 1.75 / 3.75 / 5.75 秒** —— 5 秒内有 4 次重试机会，
满足 F6-7（前提是传输侧确实恢复了）。有单测锁住这个性质。

### 7.2 播报克制（这条容易被忽略）

盲人用户听不了每 250ms 一句「正在重连」。只在三个时刻出声：

| 时刻 | 文案 | 级别 |
|---|---|---|
| 从 STREAMING 掉下来 | 「眼镜连接断开，正在重连」 | critical |
| 从未连上、连续失败 ≥3 次 | 「连接不上眼镜，请检查眼镜是否开机并靠近手机」 | critical |
| 恢复 | 「眼镜已重新连接」 | 普通 |

握手被拒（多为协议版本不符）**不重试**——重试也不会变。直接停下并说
「眼镜连接不兼容，请更新眼镜端应用」。

有单测验证「重试 10 次不再出声」和「恢复后新的掉线会重新出声」。

## 8. 端到端延迟预算落点

| 环节 | 预算 | 归属 |
|---|---|---|
| 取帧 → 编码 → 传输 → 解码 | ≤150ms | 待实测（M1 第 5/6 块） |
| 画质门控 + 目标检测 | ≤60ms | 已测 40.6ms 中位 / 50.7ms P95 |
| 距离融合 + 风险评分 | ≤20ms | 已含在现有链路内 |
| 多帧确认（2 帧 @15FPS） | ≈133ms | 设计值 |
| 下发 + 眼镜端起播 | ≤200ms | 待 M0 Q5 实测合成延迟 |

高风险走 `GLASSES_PRESET_AUDIO`（promptId + 预置音频），省掉合成耗时，目标 p95 ≤450ms。

### 10.1 下游零改动的验证方式

PRD M1 退出条件要求「下游算法零改动」。验证办法不是靠人看，而是：

`SessionReplaySource` 已经证明「离线会话能像实时相机一样被回放」。

与 `risk_events.jsonl` 是否逐条一致**。不一致就说明链路层污染了下游。

## 11. M1 退出条件

- [ ] 眼镜↔手机连续运行 **30 分钟**：不崩溃、无内存增长、`LinkFrameReader.pendingBytes()` 不持续增长；
- [ ] 主动断开 **10 次，100% 在 5s 内恢复**并有正确播报；
- [ ] 时钟对齐**收敛**，且实测 `uncertaintyNs ≤ 50ms`（否则 F6-9 不达标，需先解决链路 rtt）；
- [ ] 实测漂移代入第 5.4 节推算，确认 30s 同步周期够用；
- [ ] 传输链路延迟（取帧→解码完成）**p95 ≤ 150ms**；
- [ ] 丢帧率 **≤ 5%**（`SequenceTracker.lossRate()` + `StaleFrameGate.dropRate()` 分别报告）；
- [ ] 端到端 **p95 ≤ 700ms**，高风险 promptId 通道 **≤ 450ms**；
- [ ] **下游零改动**已用第 10.1 节的比对方式验证；
- [ ] 眼镜摘下自动暂停采集（若 Q6 判定佩戴检测可用）。
